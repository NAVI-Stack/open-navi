# NAVI Onboarding Timeline (Onboarding Experience Flow)

**Status:** Superseded by v2 spec and implementation.

The canonical onboarding spec is **[.cursor/plans/onboarding-flow-v2.md](../../.cursor/plans/onboarding-flow-v2.md)**. Implementation follows the plan **Correct Onboarding Flow** (state machine, checkpoint, phased API, setup module enforcement, Phase 8 gates, config snapshot, genesis audit).

This document is retained for historical context. During onboarding, NAVI speaks in **first person** through the **Onboarding Experience**. The Onboarding Experience is a dedicated setup/configuration module only — it does not offer or mention choosing a persona; after setup, users use the standard Persona System (Experience Layer). See **[Onboarding Experience](../concepts/onboarding-experience.md)** for the current role and behavior.

---

# Phase 0 — System Boot

**Trigger:** NAVI starts and detects no configuration.

System checks:

* `config.exists == false`
* `owner.exists == false`

Action:

* Activate **Onboarding Experience**
* `onboarding_mode = true`

The Onboarding Experience becomes the exclusive interface until onboarding completes.

---

# Phase 1 — First Contact

**Goal:** Establish context and user intent.

NAVI initiates the conversation.

Example flow:

"Hello. I am NAVI.

It looks like this is a new instance and I have not been configured yet.

The first person who completes this setup becomes my owner. My owner controls access, permissions, and configuration.

Would you like to begin setup?"

---

# Phase 2 — Ownership Establishment

**Goal:** Define the owner identity and create the first trust anchor.

NAVI gathers minimal identity information.

Possible fields:

* owner_name
* owner_handle
* owner_device_name

Example interaction:

"What should I call you?"

Followed by:

"You will become my owner. To secure me, you need to create the owner secret. This is the only shared root secret in my system."

User confirms ownership and creates the **owner secret**.

Notes:

* The first user to complete this step becomes the owner
* The owner secret is only used for owner-level recovery, bootstrap, and privileged setup flows
* Day-to-day access should not continue to rely on the owner secret

---

# Phase 3 — Initial Auth Bootstrap

After the owner secret is created, NAVI immediately generates the first API key for the owner.

This becomes the owner's normal authentication credential for API, console, CLI, and connector access.

NAVI message:

"Your owner secret has been created. I will now generate your first API key. Use API keys for normal access. Reserve your owner secret for recovery and privileged ownership actions."

Generated artifacts may include:

* owner_id
* instance_id
* owner_secret_fingerprint
* primary_owner_api_key
* recovery_seed
* signature

This is the core auth model:

* **Single owner secret** for root ownership and recovery
* **API keys** for all normal authentication after setup
* **Additional API keys** can be generated by the owner and shared with other users or systems

# Phase 3.5 — Owner Passport Creation

NAVI generates an **Owner Passport**.

The Owner Passport should not just be a dump of raw secrets. It should be a portable ownership and recovery artifact.

Contents may include:

* owner_id
* instance_id
* owner_secret_fingerprint
* primary_owner_api_key
* recovery_seed
* created_at
* signature

NAVI message:

"I have created your Owner Passport. It proves your ownership of me and contains your recovery materials.

Please save it somewhere secure."

User actions:

* Download passport file
* Copy primary API key
* Save recovery seed
* Confirm secure storage

Confirmation step:

"Have you saved your Owner Passport and primary API key?"

# Phase 8 — Recovery Setup

NAVI creates recovery mechanisms for the owner.

Recovery exists because the owner may lose their API key, device, or access path. The owner secret is the root recovery anchor, but NAVI should also support additional recovery safeguards.

Options:

* Recovery seed phrase
* Backup owner key material
* Encrypted backup file
* Secondary recovery contact or method

Prompt:

"Please choose a recovery method in case you lose your API key or access device. Your owner secret remains the root ownership credential."

Recovery principles:

* The owner secret is not the normal login method after setup
* API keys are the standard auth mechanism after bootstrap
* The owner can rotate, revoke, and create API keys
* The owner can share access by generating additional API keys
* Losing an API key should not require full instance reset if ownership can still be proven

# Authentication Model

NAVI should use a simpler and cleaner auth model than OpenClaw.

## Core rules

* There is exactly one **owner secret** created by the first owner during onboarding
* After the owner secret is created, normal authentication uses **API keys**
* The first API key is generated for the owner during onboarding
* The owner can generate additional API keys for people, devices, automations, or connectors
* The owner secret is reserved for ownership proof, recovery, and root-level actions

## Why this model is better for NAVI

Compared to a single always-used shared token, this model is more practical and more extensible:

* It separates **ownership** from **day-to-day access**
* It avoids forcing the root secret into every client or connector
* It supports controlled sharing without giving everyone the owner secret
* It makes key rotation cleaner
* It better matches NAVI's identity-bound assistant model

## Important guardrails

* Do not use the owner secret as the standard credential for API and connector traffic
* Prefer headers over query params for API key transport
* Allow API key labeling, revocation, expiration, and rotation
* Support multiple active API keys without changing ownership
* Treat the owner secret as a break-glass credential
