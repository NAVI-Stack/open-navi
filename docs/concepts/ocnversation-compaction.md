# NAVI future context compaction architecture study

The strongest public designs do **not** treat long-running continuity as “make a summary and hope.” They combine four different mechanisms: a small live working set, selective eviction of stale context, durable checkpointed execution state, and retrieval-backed reconstruction from external stores. The weak designs are the common ones: one rolling summary, one undifferentiated “memory blob,” or blind faith that bigger windows will remove the problem. Public docs and benchmarks now make this pretty clear: large windows still suffer from attention degradation, retrieval from long histories is brittle, and dialogue summaries are materially error-prone. citeturn25view0turn37view0turn30view0turn31view0turn7search0turn29view3

## Research synthesis of existing approaches

The clearest live-compaction implementation on the market is from Claude. Public Anthropic and Amazon Bedrock docs describe **server-side compaction** that triggers near a configured token threshold, writes a dedicated `compaction` block, and continues the conversation from that compacted state; Bedrock explicitly recommends this for long-running conversations and agentic workflows. Anthropic also exposes lower-risk **context editing** strategies that clear stale tool results or old thinking blocks without requiring full summarization, and its January 2026 cookbook shows a more advanced pattern: build session memory in the background so compaction is ready before the user needs it. That cookbook is notable because it admits the obvious product truth: reactive foreground compaction is a bad UX; in the demo, traditional compaction kept the user waiting for more than 40 seconds. citeturn10view2turn12view0turn20view0turn37view0turn19view0turn19view3

The public stack from entity["company","OpenAI","AI company"] is a different mix. The API offers durable conversation objects via the Conversations API, lightweight turn chaining via `previous_response_id`, and explicit guidance to carry forward tool calls, tool outputs, and reasoning items when function calling is in play. The newer Agents SDK adds sessions, resumable runs, interruptions, and an `OpenAIResponsesCompactionSession`; crucially, the docs warn that auto-compaction can block streaming and should sometimes be run manually during idle time. OpenAI’s own product memory docs also draw a line that matters for NAVI: ChatGPT memory is for saved preferences and reusable high-level facts, not exact templates or large verbatim text. That is durable memory and personalization, not active task continuity. citeturn10view5turn12view7turn13view0turn27view1turn28view1turn15view0turn15view1turn15view3

MemGPT and Letta formalize the same split more explicitly. The MemGPT paper frames context management as a **memory hierarchy** problem and proposes “virtual context management” across tiers rather than trying to keep everything in the prompt. Letta’s design makes the distinction operational: **memory blocks** are always visible in-context, while **archival memory** is an external semantic store queried on demand via tools. That is the right primitive separation for NAVI: some state must be pinned, but most history should be externalizable and retrievable. citeturn16view0turn10view14turn24view0

The runtime side of the problem is solved better in agent orchestration systems than in “AI memory” branding. entity["company","LangChain","agent framework company"]’s LangGraph persists state as checkpoints at every step, supports time travel, replay, and fault-tolerant restart, and distinguishes thread-scoped short-term state from cross-thread store-based memory. LangGraph interrupts, Amazon Web Services’ AgentCore integrations, entity["company","Microsoft","software company"] workflow checkpoints, AutoGen state save/load, and entity["company","Temporal Technologies","workflow platform company"] durable execution all converge on the same lesson: operational continuity depends on **exact resumable state**, not narrative recap. Temporal’s documentation is especially blunt: durable execution exists because application state, progress, and resume points must survive crashes and long time gaps. citeturn10view9turn10view10turn21view0turn21view1turn21view2turn10view11turn11view15turn11view16turn21view7turn21view8turn22view0

Benchmarks and research fill in the rest. LoCoMo shows that even long-context models and RAG still lag humans on very long dialogue, especially for temporal and causal understanding. LongMemEval reports roughly a 30% accuracy drop for commercial chat assistants and long-context LLMs across sustained interactions, and its proposed fixes are not “use a bigger window,” but rather better indexing, session decomposition, and time-aware query expansion. EverMemBench shows a dual bottleneck: retrieval quality and reasoning robustness. On the efficiency side, prompt-compression work such as Selective Context, LongLLMLingua, and LLMLingua-2 demonstrates real token and latency savings, while more memory-centered systems such as Mem0 and LightMem argue for tiered storage plus offline consolidation. The important caution is that many newer systems report strong internal results, but only a subset have broad production validation. citeturn30view0turn31view0turn31view2turn16view9turn17view0turn17view2turn17view4turn32view0turn18view0turn18view4

## What is proven and what breaks

**What the best existing systems appear to do during active conversations:** they keep a hot recency buffer, checkpoint exact state outside the model, evict obviously stale material such as old tool results, and only then use limited summaries or retrieval to reconstruct older continuity. Claude’s compaction plus context editing, OpenAI’s resumable conversation state plus carried-forward tool/reasoning items, Letta’s pinned memory blocks versus archival memory, and LangGraph/Temporal-style checkpoints all point in the same direction. The pattern is not “one memory system.” It is a stack. citeturn12view0turn37view0turn13view0turn10view14turn24view0turn21view0turn22view0

**What is actually proven:** durable checkpoints, resumable interrupts, session-scoped state, retrieval-backed reconstruction, prompt caching on stable prefixes, and low-touch compaction like tool-result clearing. These are all already documented, shipped, and linked to concrete latency or continuity benefits. LongMemEval’s indexing–retrieval–reading decomposition also looks credible because it is a benchmark-driven finding, not just a product pattern. citeturn10view7turn10view8turn37view0turn21view4turn27view0turn31view0

**What is plausible but not yet mature:** autonomous agent-controlled compression, demand-paging analogies for context, graph memory as a default substrate, and summary-conditioned long-horizon training schemes such as ReSum. These ideas are interesting and some early numbers are promising. ReSum reports gains over ReAct for long-horizon web tasks; Active Context Compression reports token savings without hurting performance on a tiny SWE-bench Lite sample; the “missing memory hierarchy” paper reports large production-side savings through paging and eviction. But these are still early-style results, not a settled production template for correctness-critical conversational continuity. citeturn34view1turn34view2turn35view0turn33view0turn33view1turn33view2

**The major failure modes of summary-based compaction are not hypothetical.** Dialogue summarization work finds material factual inconsistency rates, large amounts of hallucinated factual error, and a subtle class of “circumstantial inference” where the summary sounds plausible but is not directly supported by the source. Worse, LLM-based evaluators can miss these errors. In long-running agents, the practical failures are even uglier: dropped constraints, flattened alternatives, loss of exact IDs and code, temporal mis-ordering, and summary-of-summary drift. If that summary becomes the session’s source of truth, the agent is now executing on corrupted state. citeturn29view3turn29view0turn29view1turn29view2

## Key takeaways and design principles

**Context is cache, not memory.** Treat the model window as a fast, expensive working set, not as the database of record. Recent work making the “L1 cache” analogy is directionally right, and Anthropic’s own context engineering guidance says context is finite and degrades in utility as it grows. citeturn33view0turn25view0

**Execution continuity and social continuity are different problems.** Social continuity can tolerate compacted discourse notes. Active execution cannot. Tool handles, approvals, side effects, pending retries, patch state, and next execution step need typed state and checkpoints, not prose. citeturn21view4turn22view0turn11view15

**NAVI should prefer safe eviction before abstractive compression.** Old tool outputs, stale fetched documents, redundant chain items, and superseded transient reasoning are safer to clear or externalize than to rephrase. Anthropic’s context editing and tool-result clearing are the cleanest evidence for this. citeturn37view0turn25view0

**Retrieval is necessary but insufficient.** Retrieval helps reconstruct older state, but benchmarks show that retrieval failures are often about inferential relevance, temporality, and sparse evidence rather than raw vector similarity. NAVI needs retrieval plus structured state packages plus a durable event log. citeturn31view0turn16view9turn30view0

**Stable control context must be managed separately from conversation state.** OpenAI explicitly notes that instructions do not automatically persist when chaining with `previous_response_id`, while prompt caching docs from both major providers show why stable prefixes should be factored into reusable cached segments. NAVI should therefore separate static control prompts from mutable session state and never rely on chat history to carry policy. citeturn15view3turn10view7turn10view8

**Every compacted artifact needs provenance.** If NAVI cannot tell an operator where a compacted claim came from, it is not governable. Checkpoint systems already expose replay, event histories, and applied edits; NAVI should do the same for compaction products. citeturn21view1turn37view0turn22view0

## Recommended NAVI architecture

### Context tier model

NAVI should use **five operational tiers**, not a generic hot/warm/cold slogan.

**Pinned control tier.** This contains system and developer policy, safety and compliance rules, tool schemas, long-lived session configuration, and small always-on user or project preferences. This tier should be small, stable, and heavily cached. It is not allowed to accrete live conversation sludge. citeturn10view7turn10view8turn15view0

**Active working set tier.** This is the truly hot context: the last few raw turns, the current user objective, the active file or artifact snippets, the most recent tool interactions, and the current local reasoning bridge around the last user turn. Claude’s compaction docs, OpenAI’s reasoning carry-forward guidance, and Anthropic’s “recency is the active working context” guidance all support keeping this region small and fresh. citeturn13view0turn19view2turn25view0

**Structured session state tier.** This is the core NAVI invention and the part most existing chat systems only partially expose. It should contain several versioned, machine-readable ledgers: a dialogue-state frame, a task ledger, a decision ledger, a tool ledger, an approval ledger, and a recovery ledger. This tier is **not** a single summary. It is the compacted operational state package that gets assembled into the live prompt selectively. Its job is the same as checkpointed workflow state in LangGraph, AgentCore, Semantic Kernel, AutoGen, and Temporal: exact continuation. citeturn10view9turn11view15turn21view7turn21view8turn22view0

**Recall and evidence tier.** This is the durable event log and associated retrieval layer. It stores raw turns, tool calls, tool outputs, file references, external receipts, prior checkpoints, and artifact blobs. Retrieval from this tier should support semantic, lexical, temporal, and ID-based lookup. LongMemEval’s decomposition into indexing, retrieval, and reading is the right mental model here. citeturn31view0turn31view2

**Long-term memory tier.** This is where dreaming and offline consolidation write durable user preferences, reusable project knowledge, and habits that matter across sessions. It is a different store with different retention rules. ChatGPT memory, Claude Code auto memory, Letta archival memory, and AgentCore long-term memory all reinforce the same separation: durable knowledge is not a substitute for current session state. citeturn15view0turn12view5turn24view0turn11view16

### Online compaction subsystem

The online compaction path should be an **asynchronous derived-state pipeline** running beside the conversation, not a blocking foreground step. The source of truth is an append-only session event log. Every user turn, assistant turn, tool call, tool result, approval action, file mutation, and external side effect writes a structured event and a blob pointer if needed. The compactor never overwrites history; it produces derivative artifacts from it. This follows the spirit of workflow event histories and replayable checkpoints, and it keeps compaction reversible. citeturn22view0turn21view1turn37view0

The compactor should run four operations in increasing order of lossiness. First, **safe eviction**: clear stale tool results, stale fetched documents, old thinking blocks, and repeated instruction blocks, while preserving references and receipts. Second, **externalization**: move large bodies such as full file contents, full web responses, and bulky tool outputs to the recall tier, leaving handles and short evidence stubs in live context. Third, **structured distillation**: update the typed session-state ledgers. Fourth, **abstractive discourse compaction**: write concise conversational continuity notes for older talk, but only for the parts that are genuinely conversational rather than operational. Anthropic’s context editing, compaction, and background session-memory patterns strongly support this ordering. citeturn37view0turn12view0turn19view0turn19view6

NAVI should reserve a permanent **emergency path** for hard budget pressure. If the soft-path compactor is behind, the system should not freeze the conversation. Instead it should immediately assemble a minimal response context from the pinned control tier, the active working set, the last stable session-state package, and any currently open tool or approval items. That provides graceful degradation. Claude’s cookbook and the OpenAI Agents SDK warning that auto-compaction can block streaming are both evidence that compaction must be latency-aware and schedulable, not blindly synchronous. citeturn19view0turn19view3turn28view1

### Dreaming and offline consolidation subsystem

Dreaming should exist, but as an **offline promotion path**, not as the only compaction path. Its job is to review completed or stale session logs and promote durable learnings into long-term memory: preferences, reusable procedures, project facts, stable relationships, and maybe higher-order abstractions. LightMem’s “sleep-time update,” AgentCore’s background long-term extraction, and Claude Code’s auto memory all fit this role. None of them justify outsourcing live continuity to sleep. citeturn18view0turn11view17turn12view5

For NAVI, dreaming should be allowed to read from the event log, checkpoints, and session-state ledgers, then write back only to the long-term memory tier. It must never rewrite or collapse the active session source of truth. That keeps offline reflection useful without contaminating current execution with delayed or speculative abstractions. citeturn18view0turn11view16turn15view0

### Active session checkpoint model

An **active session checkpoint** should be created at turn boundaries, after meaningful tool-use clusters, after approval boundaries, after file-write groups, and on idle windows if the background system is healthy. Each checkpoint should include: the active working-set slice, the versioned session-state ledgers, the set of open tool handles, the last stable response boundary, and references to any large artifacts externalized since the previous checkpoint. This is closest to LangGraph’s super-step checkpoints and Microsoft’s workflow checkpoints that capture executor state, pending messages, pending requests, and shared state. citeturn21view1turn21view7

The session checkpoint must be **provider-agnostic**. If NAVI switches models, providers, or context sizes, the checkpoint should still be loadable because it stores normalized application state, not hidden provider internals. Provider-managed conversation state can be used as an optimization, but not as the only durable continuity mechanism. OpenAI’s server-managed continuation and Claude’s server-side compaction are useful accelerators; they are not enough for governance and provider portability. citeturn10view5turn15view2turn20view0

### Task and workflow checkpoint model

A **task/workflow checkpoint** should be separate from the session checkpoint. It should capture explicit task identity, current plan version, completed steps, pending steps, blockers, open questions, acceptance criteria, idempotency keys, external transaction IDs, compensating actions, and the next safe continuation step. This is where NAVI preserves active execution continuity even if the surrounding social conversation gets heavily compacted. Workflow engines already treat this kind of state as first-class because it is what survives crashes and long pauses. citeturn22view0turn21view7turn21view8

Tool state, proposal state, approval state, and recovery state should survive compaction through dedicated ledgers:

- **Tool ledger:** tool name, parameters or hashed parameter refs, result refs, active sessions/handles, side-effect status, replay policy, and whether the result is re-fetchable.
- **Proposal ledger:** proposal ID, version, diff summary, requested decision, rationale, acceptance criteria, and provenance refs.
- **Approval ledger:** approver, timestamp, exact decision text, scope, and whether continuation was resumed.
- **Recovery ledger:** last known-good checkpoint, uncertain side effects, verification steps, retry count, and compensating actions.

This design is directly aligned with interrupts and resumable state in LangGraph and the OpenAI Agents SDK, plus general durable execution behavior in Temporal. citeturn21view4turn27view0turn22view0

### Compaction triggers, budget management, recovery, provenance, and observability

Compaction should trigger on **soft budget pressure**, **hard budget pressure**, **tool-result accumulation**, **subtask completion**, **approval boundaries**, **handoffs**, and **idle-time opportunities**. Token thresholds alone are not enough; a single search-heavy step can bloat context faster than ordinary chit-chat. Anthropic’s APIs expose trigger thresholds for compaction and tool-result clearing for exactly this reason. citeturn20view0turn37view0

Budgeting should be explicit. NAVI should reserve stable headroom for the next model output and any immediate tool loop, then allocate the remainder dynamically across the pinned tier, hot working set, structured state, and retrieved evidence. A good default is to keep at least **20–30% headroom** unused, then scale the structured state and evidence share up or down by task class. Prompt caching belongs here too: static control prefixes, stable tool schemas, and semi-stable session-state prefixes should be separately cacheable. citeturn10view7turn10view8turn25view0

Recovery should be checkpoint-first, not summary-first. On resume after failure or long delay, NAVI should load the last stable task/workflow checkpoint, reconcile open tool and side-effect state against the external world if necessary, then pull only the relevant evidence from the recall tier. If external effects are uncertain, the agent should enter a reconciliation mode instead of guessing. That is standard durable workflow behavior and far safer than trusting a prose handoff. citeturn22view0turn21view0turn21view4

Every compacted or retrieved item included in live context should carry **source references** back to session event IDs or artifact hashes. Operators should be able to inspect “why is this in context,” “which raw events produced this ledger entry,” and “what was dropped.” Anthropic’s `applied_edits`, LangGraph replay/time-travel, and Temporal event histories all point toward the same governance baseline: if the context system cannot be audited, it will fail in production when something goes wrong. citeturn37view0turn21view1turn22view0

Observability should include at least: token spend by tier, cache hit rate, compaction latency, added p95 turn latency, retrieval hit quality, correction rate after compaction, frequency of repeated user clarification, checkpoint resume success, stale-handle failures, approval replay failures, and emergency-compaction frequency. There is no serious production compaction system without this instrumentation. The public systems increasingly expose the pieces; NAVI should unify them. citeturn10view7turn20view0turn27view0

## Compaction policies by conversation and task class

**Simple social conversation.** Keep the last few turns verbatim, preserve user-facing commitments and interpersonal context, compress older small talk aggressively, and treat durable personal facts as long-term memory rather than active-session state. What matters here is tone continuity, preferences, and unresolved personal references; style and social detail are also exactly the kinds of things current memory systems struggle to extract perfectly from long histories, so NAVI should prefer preserving recent raw turns over clever inference. citeturn15view0turn15view1turn16view9

**Technical planning.** Keep requirements, constraints, assumptions, decision points, open questions, and rejection rationale in the structured decision and task ledgers. Preserve especially important requirement text verbatim when wording matters. Compress redundant paraphrase and brainstorming, but do not compress away the exact constraint language that later design choices depend on. LongMemEval’s emphasis on temporality and knowledge updates is directly relevant here. citeturn31view0turn30view0

**Coding and debugging.** Preserve stack traces, failing assertions, exact commands, file paths, patch hunks, environment facts, and unresolved bug hypotheses verbatim or in exact structured fields. Compress explanatory chatter around them. Claude’s own compaction docs allow custom instructions like “preserve code snippets, variable names, and technical decisions,” which is exactly right; code work is where lossy paraphrase does the most damage. citeturn20view0turn12view1turn25view0

**Multi-step execution.** Preserve workflow progress, side effects, receipts, external IDs, pending retries, and next safe continuation step in the task/workflow checkpoint. Old tool outputs can usually be externalized if the result is re-fetchable, but the operational receipt cannot. This is the domain where compaction policy must look most like workflow orchestration and least like chat summarization. citeturn21view7turn22view0turn21view4

**Proposal and approval workflows.** Preserve proposal versions, exact approval asks, explicit decisions, scope boundaries, and approver identity. Do not let a summary rewrite “approved if X” into “approved.” Interrupt/resume models from LangGraph and the OpenAI Agents SDK are the correct conceptual base: approval is a state transition, not a narrative flourish. citeturn21view4turn27view0

**Multi-agent systems.** Maintain a shared task blackboard and shared artifact registry, but keep per-agent local working context separate. Handoffs should pass typed contracts: objective, assumptions, artifact refs, constraints, ownership, and status. Do not hand one agent’s free-form summary to the next agent and call that coordination. Multi-agent frameworks already serialize teams, agents, and handoff state; NAVI should use the same discipline. This is an architectural inference from the runtime patterns in AutoGen and the OpenAI Agents SDK, not a claim that any current product has solved it completely. citeturn21view8turn27view0turn27view2

Across all classes, the basic rule set should stay stable. **Keep verbatim:** recent user instructions, exact approvals, code patches, errors, IDs, external receipts, unresolved commitments, active constraints. **Compress:** redundant explanation, stale social chatter, old brainstorming, re-derivable intermediate reasoning. **Retrieve on demand:** full old documents, old tool outputs, large files, archived transcripts, and long-term reference knowledge. citeturn37view0turn24view0turn15view0

For conversations that continue for hours or days, NAVI should not try to preserve “one immortal chat.” It should preserve a chain of session checkpoints and task checkpoints, keep the event log durable, promote stable learnings to long-term memory, and assemble a bridge packet on resume: last stable task state, delta since last checkpoint, relevant social context, and retrieved evidence. Durable execution systems already show the right shape here: some runs last seconds; others last months or years; the only sane model is resumable state, not ever-growing prompt history. citeturn22view0turn10view5turn11view16

## Alternative designs considered and rejected

**Rejected: foreground summarization as the default live path.** The product evidence is already bad enough here: Anthropic’s own cookbook shows reactive compaction causing large waits, and dialogue summarization research shows fact drift and hallucination. NAVI should not pay latency to generate an unreliable artifact and then trust it as the continuation substrate. citeturn19view3turn29view0turn29view3

**Rejected: dreaming-only compaction.** Sleep-time consolidation is useful, but offline abstraction cannot help the next live turn if the system is already under context pressure. LightMem explicitly separates online versus sleep-time update; AgentCore splits short-term and long-term memory; ChatGPT memory is durable preference memory, not exact active execution state. Dreaming is a complement, not the live continuity engine. citeturn18view0turn11view16turn15view0

**Rejected: one giant rolling summary blob.** This destroys inspectability, mixes social and operational continuity, and amplifies summary-of-summary corruption. It also breaks portability because every provider/model combination will compress and interpret that blob differently. The benchmark and faithfulness literature is too clear to ignore. citeturn29view3turn29view2turn30view0

**Rejected: RAG-only reconstruction of active state.** Retrieval is necessary, but EverMemBench and LongMemEval show why it is not enough: relevance is often temporal, inferential, or versioned rather than lexically obvious. A missed approval condition or expired tool handle is not something you want to discover because vector search failed. citeturn16view9turn31view0

**Rejected: provider-managed hidden state as the only continuity layer.** Server-managed continuation is convenient, but it is opaque, provider-specific, and insufficient for governance. NAVI should use it when helpful, but only atop its own normalized checkpoints and event log. citeturn10view5turn20view0turn27view1

The main failure modes NAVI still needs to guard against are predictable. Summary drift is mitigated by typed ledgers and provenance. Retrieval miss is mitigated by hybrid indexing with temporal and ID lookups. Context thrashing is mitigated by pinning the working set and degrading gracefully instead of over-evicting. Side-effect ambiguity is mitigated by a recovery ledger and reconciliation mode. Approval corruption is mitigated by exact, immutable approval records. Provider differences are mitigated by keeping provider-managed state as an optimization, not the canonical state. citeturn33view3turn31view0turn21view4turn22view0

## Phased implementation roadmap and evaluation rubric

**Build now.** The first phase should deliver the boring, high-leverage pieces: an append-only session event log; normalized session and task checkpoint schemas; a policy-aware context assembler; safe eviction of stale tool results and bulky artifacts; prompt caching for pinned prefixes; and operator-visible provenance for every assembled item. This matches what current production-facing systems actually expose and what benchmarks say matters. citeturn37view0turn10view7turn21view0turn31view0

**Build next.** Add the asynchronous compaction worker, typed dialogue and approval ledgers, retrieval over the event log with temporal and ID-aware indexing, emergency-compaction fallback, and multi-turn resume tests. At that point NAVI has a real live compaction subsystem rather than heuristic buffering. citeturn19view0turn19view6turn31view0

**Build later.** Add dreaming, more sophisticated long-term memory promotion, multi-agent shared blackboards, and experimental compaction policies such as adaptive or agent-assisted compression. Interesting ideas like graph memories, autonomous context compression, and paging-style working-set models belong here, after the exact-state foundation is stable. citeturn18view0turn34view1turn35view0turn33view0

**Evaluate with a rubric that separates continuity from personalization.** NAVI should score itself on: accurate retrieval; long-range and temporal reasoning; knowledge update and contradiction handling; abstention when evidence is missing; state-fidelity across compaction boundaries; approval correctness; resume-after-failure; p95 added turn latency; token reduction; and user-repeat rate. LongMemEval, LoCoMo, and MemoryAgentBench are useful templates because they test more than raw recall; they test temporality, updates, abstention, and selective forgetting. citeturn31view0turn30view0turn16view10

The first real compaction subsystem for NAVI should therefore look like this:

- A **NAVI Context Runtime** that records every turn, tool interaction, and state transition into an event log. citeturn22view0turn21view1
- A **Checkpoint Engine** that emits both session checkpoints and task/workflow checkpoints. citeturn21view0turn21view7
- A **Compaction Worker** that performs safe eviction, externalization, structured distillation, and only then selective discourse summarization. citeturn37view0turn12view0
- A **Context Assembler** that composes pinned control, active working set, typed ledgers, and retrieved evidence under an explicit token budget. citeturn25view0turn31view0
- A **Recovery Layer** that reconciles uncertain side effects and resumes from the last safe checkpoint instead of guessing from prose. citeturn22view0turn21view4
- An **Inspection Surface** that shows what was kept, what was dropped, and why. citeturn37view0turn21view1

That is the first subsystem worth shipping. Anything less is just a nicer way to lose state.

## Why this design is better than ‘summarize in the foreground’ and better than ‘dreaming-only compaction.’

Foreground summarization is inferior because it burns user-facing latency right when the system is under pressure, and the artifact it produces is exactly the kind of thing dialogue-summarization research says is vulnerable to omission, hallucination, and unsupported inference. Dreaming-only compaction is inferior because it solves the wrong time horizon. Offline consolidation is good for durable personalization and long-term learning, but it does nothing for a live session that is about to exceed its working budget while active tools, approvals, and execution state are in flight. Public systems that separate short-term state from long-term memory all imply the same answer: active continuity needs online state management now; dreaming can shape what survives later.
