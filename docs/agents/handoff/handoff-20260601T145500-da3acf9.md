## What was done

### Per-connector sync policy (CIP §7 / §7.1)

- `internal/schema/intake_policy.go` — canonical `SyncPolicy` with separate
  `Backfill` and `Delta` `SyncModePolicy` blocks (cadence, budget
  {max_records_per_pass, max_bytes_per_pass, cost_ceiling_usd}, cursor strategy,
  dedupe rule, freshness window) + `PrivacyClass` + `Visibility`. Cadence/freshness
  duration parsers (manual/webhook-triggered → no fixed interval). Types live in
  `internal/schema` per the P1/P2 cycle-breaking convention so `internal/store`
  can persist overrides without importing `internal/intake`.
- `internal/intake/policy/` — `DefaultPolicy` (Telegram + generic defaults),
  `Validate`, `merge` (non-zero overlay), `LoadDir` (config/connectors YAML),
  `Resolver` (default → file → store-override precedence), `Pass` (per-pass budget
  accumulator + `CanAdmit` + `ToLogEntry`), `EstimateRecordCostUSD`, and the
  backfill consent manager (`RequestBackfill`, `ConsentState`,
  `StartApprovedBackfill`).
- `internal/store/connector_sync_policy.go` — raw-SQL runtime-override store
  (full policy JSON keyed by connector id; configuration, not entity state).
- `config/connectors/telegram.yaml` — default Telegram policy (webhook-triggered
  delta, manual backfill, 30d freshness) overlaying the Go default.

### Sync log (CIP §11; Vault §13)

- `internal/schema/intake_sync_log.go` — `IntakeSyncLogEntry`, `VaultSyncLogEntry`,
  terminal-status enum (running/completed/budget_exceeded/cost_ceiling/
  consent_rejected/consent_pending/error).
- `internal/store/intake_sync_log.go` + `internal/store/vault_sync_log.go` —
  append-only stores (intake populated by the worker; vault is **schema + store
  only**, populated by the parallel Vault deliverable).
- `internal/store/db.go` — three new tables (`connector_sync_policy`,
  `intake_sync_log`, `vault_sync_log`) + covering indexes.

### Worker enforcement (`internal/intake/worker.go`, `worker_passes.go`)

- Sources `PrivacyClass` from policy at Admit (new `AdmitRecordWithDefaults`;
  `AdmitRecord` delegates with the old `personal` default).
- Per-pass record/byte budget enforced at the consumer boundary: exceeding it
  **terminates the pass cleanly** (writes a `budget_exceeded` sync-log row) and
  opens a fresh pass — lossless segmentation, since dropping inbound user messages
  is unacceptable for an event-driven connector.
- Per-connector **cost ceiling** routed through the existing Governor
  (`Governor.RecordConnectorCost` — new, additive; reuses `ErrGovernorTripped`/
  `GovernorCostCeiling`). A trip is the hard halt: the pass closes with
  `cost_ceiling`, the offending record is dropped, the connector cost resets so a
  later pass can proceed (cost ceiling is per-pass per CIP §7).
- One `intake_sync_log` row per connector activity window (closed on the 30s
  flush ticker, on shutdown, or on a budget/cost event). Documented as the
  "one row per pass" choice in `worker_passes.go`.

### Backfill consent (CIP §7.1; synthesis seam §12)

- `RequestBackfill` raises (or reuses) a consent Proposal in the **one** existing
  queue, tagged `source_process: intake_consent`, describing scope/budget/freshness;
  offers **resume-from-cursor** when the connector already has historical state.
- `StartApprovedBackfill` gates execution on owner approval; a declined Proposal
  writes a `consent_rejected` sync-log row; pending/absent → no start.

## What was not done

- **Vault content/population** — out of scope (parallel deliverable). P5 ships the
  `vault_sync_log` schema/store, the `GET /api/vault/sync-log` endpoint, and the
  drift-report UI hook; the Vault writes the rows.
- **Telegram historical backfill puller** — the consent gate, resume-from-cursor
  Proposal, and `intake_sync_log` accounting are real and tested, but there is no
  Telegram historical-message fetcher (connectors-not-implemented is out of scope).
  Approving a backfill Proposal authorizes a pass; wiring an actual historical
  pull is future work.
- **Connector-id reconciliation nuance** — the connector-detail panel keys on the
  capability-graph connector id (e.g. driver `telegram`), while emitted records/
  sync-log rows use the account-scoped id (`telegram:acct-1`). Policy resolves
  correctly for both (driver-prefix defaults), but last-pass metrics only match
  when the ids align. A future iteration should map instance → emitted id.
- **`-race`** — host has no cgo (unchanged from P3/P4). P5's only added concurrency
  is the pass map, guarded by `w.passMu`.
