NAVI Architecture Guide

A living, code-grounded visual guide to NAVI: local-first AI runtime, daemon, CLI, browser console, governance, inference control, tools, world model, persistence, workers, connectors, and deployment boundaries.

Status: Active Last Reviewed: 2026-06-02 Repo: NAVI-Stack/NAVI Default branch: master Primary runtime: Go 1.24 Living document

1. Executive Architecture Overview

NAVI is implemented as a local-first personal AI runtime. The long-running daemon is NaviD, while NaviExe and the browser Console act as clients through the gateway contract. The repository is Go-first, with a TypeScript/React Console, Docker deployment targets, SQLite persistence, embedded NATS messaging, plugin-owned connectors/providers, and optional Python skill execution support.

The implemented architecture is centered around a persistent NAVI agent loop, a runtime coordinator, a deterministic Governor, and a first-class Inference Control System (ICS). The ICS constrains model calls and tool execution through governed envelopes, model directives, tool contracts, and permits. World Model state is persisted through SQLite-backed store helpers and projected into inference context through facts, memory, retrieval, reflection, intake, and the Memory Vault path.

5. Governance Layer Deep Dive

What the Governor Controls

  • Action budget, retry limit, cost ceiling, autonomous duration, repeated-response tripwire.
  • Workspace path safety through absolute-path rejection, symlink resolution, and workspace escape checks.
  • Governed action validation for skills, workers, connectors, gateway commands, and world-model mutations.
  • Proposal boundaries for intent-changing actions, code modification, communication, tombstone, owner-set fact supersede/deprecate.
  • Connector intake cost enforcement.

internal/governor/governor.go, internal/governor/validate.go

Governance Shape

Centralized but distributed in use. The Governor and validation pipeline are centralized Go code, but callers include ICS, worker authorization, file/tool path checks, intake synthesis, Memory Vault edits, and gateway/operator flows.

Current maturity: implemented core. Configuration and priority alignment exist as pipeline stages, but configuration-specific validation is thin and some checks are tag/simple-text based. Treat this as implemented infrastructure with partial policy depth.

cmd/navid/main.go, internal/navi/inference/validate_govern.go, internal/governor/validate.go

6. Inference Control System Deep Dive

AssembleInput

Runtime assembly loads run/session/checkpoint state, prior envelope, governance state, recovery state, visible capabilities, and relevant context.

Decide

ICS selects focus, route/mode, candidate, rationale, execution intent, governance handoff, and recovery/reflection scaffolding.

Validate / Govern

Selected candidate goes through deterministic governance. Reject, approve, modify, or create proposal and pause.

PrepareModelCall

ICS narrows model-visible tool surface into a ModelDirective and requires ToolContracts for executable tools.

CallModel

Runtime compiles prepared request, calls selected provider/model, and normalizes the response.

AuthorizeModelResponse

ICS rejects out-of-bound or contractless tool calls and emits AuthorizedToolInvocation + ToolPermit when safe.

ExecuteAuthorizedAction

Runtime executes only a matching permit/contract pair. Raw model tool calls are not executable authority.

ObserveOutcome + PersistState

ICS supervises execution snapshot and runtime persists DecisionEnvelope and history for replay/resume.

Runtime dispositions: call_model, pause_for_proposal, block_with_reply, and proceed_direct. These are first-class execution boundaries, not prompt suggestions.

7. Tools System Deep Dive

Registration and Discovery

The tool registry is the first-class catalog for file tools, skills, plugins, self-mod tools, and builtins. It enforces collision detection, aliases, snapshot IDs, registration order, source replacement, domain/source listing, and LLM-facing definitions.

internal/tool/registry.go, internal/tool/types.go

Execution and Safety

Execution occurs through a registered ToolExecutor, but runtime safety depends on ICS: ModelDirective limits visible tools, ToolContract defines executable semantics, ToolPermit authorizes a concrete call, and runtime fails closed on mismatch.

internal/navi/inference/model_authorization.go, internal/navi/runtime_executor.go

Tool Metadata

Tools carry source, schema refs, category, authority, status, visible surfaces, connector dependencies, risk tier, side effects, reversibility, domain, workspace action, confirmation requirement, trust tier, and interaction modes.

External Integrations

Plugin and connector registration ties tools to Telegram, Slack, LLM providers, Docker-backed sandbox behavior, Python subprocess skills, and future extension points.

10. Request / Execution Flows

Normal User Request Flow

Console or CLI sends chat request to Gateway.
Gateway authenticates and calls NAVI message input path.
Runtime session/inbox records the message.
Agent loop assembles context, facts, retrieval, capabilities, and prior ICS state.
ICS governs model/tool boundary and runtime calls model if allowed.
Response/tool events persist to SQLite and stream/live-update back to clients.

Tool Execution Flow

Tool registry exposes filtered definitions to model via ICS ModelDirective.
Model returns tool call; runtime normalizes it but does not execute it.
ICS validates tool attempt against boundary, contract, workspace/action rules, and Governor.
If approved, ICS emits ToolPermit and AuthorizedToolInvocation.
Runtime executor checks permit/contract match, calls registry Execute, and captures ToolResult.
ICS observes outcome and persists updated envelope/history.

World State Update Flow

Connector, Vault edit, reflection, or runtime event produces intake/reflection input.
Intake worker admits, dedupes, scores, embeds, extracts, resolves, synthesizes, and folds.
World-model mutation effect routes through Governor and autonomy policy.
Approved writes update store/worldmodel; hard-floor writes create proposals.
Facts/memories become available to context blocks and retrieval for future inference.

Startup / Bootstrap Flow

Load config and env overrides.
Open SQLite, run migrations, seed sandbox profiles.
Initialize identity and onboarding state.
Create WorldModel, start/connect NATS, load plugins/connectors/providers.
Create LLM control plane, Governor, chat/runtime store, NAVI agent.
Start heartbeat, cron, backlog poller, orchestrator, workers, reflection, intake, vault, gateway, connectors.

15. Known Unknowns

  • Full file tree and circular dependency analysis were not exhaustively generated from a local clone in this review. The component map is grounded in key files and docs reviewed through GitHub access.
  • Some implementation files referenced by ICS mapping, such as runtime_inference.go, runtime_executor.go, model_authorization.go, and outcome_supervisor.go, were mapped from repository docs and related code but not fully line-by-line audited here.
  • Memory Vault startup was observed in the daemon bootstrap and config comments, but the complete vault worker implementation was not fully reviewed in this pass.
  • PET is described as a client using the gateway contract, but its implementation appears to live outside the core NAVI repository.
  • Security claims should be revalidated before deployment outside trusted local owner environments.
