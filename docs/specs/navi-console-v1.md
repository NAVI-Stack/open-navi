# NAVI Console V1 Implementation Spec

**Status:** Draft  
**Last Updated:** 2026-05-06  
**Updated By:** NAVI Console reconciliation  
**Source of truth target:** `cmd/navid/main.go`, `internal/gateway/server.go`, `internal/gateway/middleware.go`, `internal/config/config.go`, `config/runtime.yaml`, `web/`, `web-src/navi-console/`

NAVI Console V1 is the local, backend-hosted runtime inspection and control surface served by the existing NAVI gateway.

This spec narrows the implementation target from the broader [NAVI Console design](../design/navi-console.md) and follows [ADR-010](../adr/ADR-010-navi-console-gateway-hosting.md).

---

## Scope

V1 provides a local operator console without introducing a separate server or bypassing current gateway governance.

V1 includes:

- static frontend served by the existing gateway at `/`
- local URL: `http://127.0.0.1:6284/`
- frontend source under `web-src/navi-console/`
- generated build output under `web/`
- reuse of existing gateway APIs
- live runtime updates through `/ws/live`
- runtime clarity pages for inspection, governance, usage, scheduling readiness, configuration, appearance, and docs
- read-first UI, with state-changing controls only where current endpoints support them

V1 does not include:

- public-hosted console mode
- separate console auth/session server
- separate `/api/v1/*` API namespace
- full theme marketplace/builder
- scheduler CRUD management without backend route support
- live Markdown documentation rendering

## Existing Runtime Facts

Current implementation already provides the required hosting foundation:

- `gateway.Config` has `Addr` and `StaticDir`.
- `gateway.NewServer` defaults `Addr` to `:8080` only when unset.
- `gateway.NewServer` defaults `StaticDir` to `web` only when unset.
- `internal/gateway/server.go` registers `GET /` as static serving from `gateway.static_dir` with first-run onboarding redirect behavior.
- `config/runtime.yaml` sets `gateway.addr: ":6284"` and `gateway.static_dir: "web"`.
- `internal/config/config.go` defaults gateway config to `:6284`, `web`, and localhost CORS origins.
- `internal/gateway/middleware.go` grants loopback requests local owner/admin-style access and otherwise uses API-key/shared-secret auth.
- `web/onboarding.html` is committed static content and must remain available in Docker/runtime images.
- `web/index.html` and `web/assets/` are generated console build output and should remain ignored by Git.

Therefore, V1 attaches to the existing gateway instead of creating a second listener.

## Static Frontend Contract

Source/output shape:

```txt
web/
  onboarding.html        # committed first-run shell
  index.html             # generated by console build
  assets/                # generated by console build

web-src/navi-console/
  package.json
  package-lock.json
  src/
  vite.config.ts
```

The Vite console build writes to `../../web`. Generated `web/index.html` and `web/assets/` are ignored by Git; they are produced by `make build-console`, `make build-all`, and the Docker frontend build stage.

The frontend uses hash routing so backend SPA fallback changes are not required for direct page access.

---

## Authentication Contract

The console uses existing gateway auth behavior.

Local loopback:

- Requests from loopback are treated as local owner/admin access by middleware.
- The console can run without asking for an API key when served from `127.0.0.1:6284` or `localhost:6284`.

Non-loopback:

- Must require existing API key or shared-secret behavior.
- V1 does not add public-hosted browser session auth.
- Public/non-loopback console hosting remains out of scope until a hardening pass covers TLS, browser session auth, CSRF, origin policy, and loopback-bypass review.

State-changing actions:

- Must use current gateway endpoints.
- Must not bypass existing handler-level owner-secret or scope checks.
- Must preserve proposal/governance behavior.

The browser-hosted console provides quick-add controls for local, repo, and protected paths. Native browser folder pickers do not expose absolute filesystem paths to web pages, so browser folder selection is advisory. The Server path browser asks NaviD to list directories it can see and fills the absolute server-visible path. In Docker Compose, that means container paths and mounted host folders; unmounted host folders are not usable workspace boundaries until they are bind-mounted or mapped.

## Remaining Gaps

- Scheduler CRUD API is absent; Scheduler remains inspection/readiness-only.
- Docs live Markdown rendering is absent; Docs uses curated help and copyable repo paths.
- Usage token/cost accuracy depends on fields returned by runtime metrics, governor, and run payloads; the UI must not invent estimates.
- Public/non-loopback Console hosting remains out of scope.
- Capability graph failures are handled as degraded state, but capability graph completeness depends on the ongoing capability expansion work.
- Appearance persistence currently targets Console UI preferences only; propagation to PET/mobile/future frontends remains future work.
- Direct route query parameters are intentionally limited because the app uses simple hash routing.

## Live Event Handling

V1 connects to:

```txt
GET /ws/live
```

Requirements:

- connect after initial page load
- reconnect with backoff
- expose connection state in UI
- avoid crashing on unknown event types
- retain a bounded in-memory event buffer
- allow pages to render waiting/degraded states honestly

Event rendering starts generic:

```txt
time | type/kind | chat/run | summary | raw JSON
```

## API Error Handling

The console must handle both current error shapes:

```json
{"error":"message"}
```

and structured operator-shell errors:

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "details": {}
  }
}
```

UI behavior:

- show HTTP status
- show error message
- preserve raw response in expandable details
- never report success for partial/failed operations
- avoid rendering false empty states when the endpoint actually failed

## Backend Implementation Requirements

V1 keeps backend edits narrow.

Allowed backend edits:

- static serving/onboarding redirect behavior
- route docs updates when routes change
- small, bounded routes required by implemented Console surfaces, with tests and docs
- tests for onboarding/static/auth behavior

Avoid backend edits:

- new console server
- separate console auth middleware
- duplicate `/api/v1/*` namespace
- scheduler CRUD without a dedicated backend feature plan
- live Markdown docs serving without a dedicated docs feature plan

## Acceptance Criteria

### Static hosting

- `make build-console` produces generated Console assets under `web/`.
- `make build-all` includes Console build.
- Docker build stage builds the Console and preserves committed `web/onboarding.html`.
- `go run ./cmd/navid` serves Console assets from `gateway.static_dir`.
- `http://127.0.0.1:6284/` loads the Console after first-run setup.
- Missing assets produce normal static-file errors.
- API routes are not captured by static serving.

### Onboarding

- Fresh first-run `/` redirects to `/onboarding`.
- `/onboarding` is local-only.
- `/api/onboarding/*` is local-only and bypasses API-key auth only for first-run browser flow.
- Completing onboarding redirects back to `/`.
- Recovery/passport handling does not expose secrets beyond the intended one-time response.

### Runtime Console

- Overview gives useful at-a-glance runtime state.
- Chat can create/select chats and send messages.
- Chats can inspect detail/runtime summary and archive where supported.
- Projects can inspect readiness, bind workspaces, create project chats, and create project tasks.
- Workspaces can inspect/set operating mode, active workspace, boundary roots, allowed actions, and whitelist rules.
- Logs can inspect activity/events/errors/live feed.
- Debug can inspect raw runtime diagnostics.
- Capabilities renders capability graph data or visible degraded state if unavailable.
- Proposals can approve/decline through the proposal lifecycle.
- Usage summarizes available runtime usage data without inventing missing cost/token estimates.
- Scheduler reports management unavailable and remains useful in inspection/readiness mode.
- Docs explains Console surfaces and known gaps without broken repo-doc links.
- Config exposes identity, experience, presence, and LLM state.
- Appearance saves, loads, applies, and resets Console UI preferences.

### Docs hygiene

- `docs/design/navi-console.md` remains the broad product design.
- `docs/adr/ADR-010-navi-console-gateway-hosting.md` remains the architecture decision.
- this spec remains the V1 implementation contract.
- `docs/specs/gateway-api.md` remains the live gateway route inventory.
- `docs/specs/INDEX.md` includes this spec.

## Test Guidance

Backend tests:

- `/` redirects to `/onboarding` when first-run is incomplete.
- `/` serves static Console content when first-run is complete and build output exists.
- `/onboarding` and `/api/onboarding/*` reject non-local requests.
- `/api/*` routes are not captured by static serving.
- chat rename accepts valid titles and rejects empty/unknown chats.
- appearance preferences default, persist, reject invalid payloads, and enforce auth/scope behavior.

Frontend/manual smoke:

- `make build-console`
- `make build-all`
- Docker image serves Console and committed onboarding shell
- Console loads on `127.0.0.1:6284`
- Overview endpoints render
- Chat create/message works
- Chats detail renders
- WebSocket connects or reports failure clearly
- Proposal resolve failure/success paths render
- Capabilities graph renders or reports degraded state clearly
- Scheduler reports management unavailable and graph-degraded inspection state without false empty-tool claims
- Appearance preferences save, load, and apply to major pages
- Usage shows token/cost unavailable when backend fields are absent
- Docs page renders copyable repo doc paths
- raw JSON panels do not crash on unknown payloads

## Open Questions

- Should onboarding and Console become one SPA later, or should onboarding remain a committed static shell?
- Should future durable appearance preferences live only under Console settings, or propagate through Experience/Configuration for PET/mobile surfaces?
- Should Scheduler CRUD become a dedicated backend feature before any management UI ships?
- Should live Markdown docs rendering be served by the gateway or remain repo/developer-tooling only?
- Should hash routing gain query-param support for deep-linking selected chats/proposals/runs?
- Should capability graph become mandatory for Capabilities page, or should legacy skills/tools/plugin/connector fallbacks remain first-class?
